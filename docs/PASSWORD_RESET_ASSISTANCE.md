# Password reset assistance

Employees and administrators can open **Forgot Password → Request administrator
assistance** and submit their registered email. The response is generic for
unknown, inactive, ineligible, duplicate, and accepted accounts. Public requests
are not authenticated identity claims. Super-admin recovery is excluded.

In **System Administration → Password Reset Requests**, the super-admin can
filter Pending, Sent, or Closed requests. Before sending a code, verify the
requester using the municipality's established identity verification procedure
and confirm the verification checkbox. The code goes only to the registered
email; there is no editable destination or password field. If the user cannot
access that email, use a separate verified account-recovery process.

The open queue updates through the authenticated app WebSocket after committed
creation, sending, closing, or reset completion. Events are limited to super-admin
sessions and contain no account details or codes. It reloads the current filter
and page, defers updates during confirmation/actions, refreshes after reconnect
or app resume, and polls every 30 seconds to recover missed events. Leaving the
page cancels its subscription and timer. Multiple backend processes rely on the
polling fallback for events generated by another process.

The user selects **Enter a reset code** in Forgot Password and chooses their own
password. Existing SMS recovery remains available. Sending a new SMS or email
code invalidates prior codes. Closing an assistance request invalidates its
outstanding email code. Completing a reset closes open assistance requests,
consumes outstanding codes, revokes refresh tokens, increments `auth_version`
to invalidate issued access tokens, and disconnects local app-event sockets.
The next protected API request prompts an old session to authenticate again.

## Installation

Before deploying the backend, apply only
`backend/scripts/migrations/20261004_password_reset_assistance.sql` to the intended
database. From `backend`, with PostgreSQL connection environment configured:

```sh
psql -v ON_ERROR_STOP=1 --single-transaction -f scripts/migrations/20261004_password_reset_assistance.sql
```

It adds `users.auth_version`, `password_reset_requests`, and the OTP-to-request
reference. It assumes the existing OTP table is installed. Fresh installations
include it in `init-schema.sql`. Deploy the backend and rebuild the frontend.
The existing audit identity migration should also be installed for historical
actor/target names. No SMTP credentials are changed by this feature.

Assisted delivery uses existing `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`,
`SMTP_PASS`, and `SMTP_FROM` settings. SMTP socket/connection timeouts are bounded
for assisted sends. No OTPs are returned to administrators or logged. Codes are
stored as HMAC hashes and share existing reset TTL, digit, attempt-limit, and
password-length settings. Default expiry is five minutes and five incorrect
attempts consume a code. Public requests use the existing IP reset limiter;
one open request per account, a 15-minute request cooldown, and a 60-second resend
cooldown are enforced in PostgreSQL. Missing SMTP configuration and send failures
leave the request retryable. The UI displays the backend error.

Audit actions: `password_reset_assistance_requested` (unverified public source),
`password_reset_assistance_sent` (handling administrator),
`password_reset_assistance_closed`, and `password_reset_completed` (account that
proved code possession). Audit details contain request IDs and workflow metadata,
never codes or passwords.

## Operational limits

- SMTP acceptance cannot guarantee inbox delivery. Email and PostgreSQL cannot
  commit atomically: if a send succeeds but commit fails, the delivered code is
  unusable and the administrator must retry. Do not treat a Sent request as a
  completed reset; completion has its own timestamp.
- Socket disconnects target the current single backend process. A multi-process
  deployment needs cross-process disconnect messaging. HTTP and reconnect checks
  use the database version. An already-running request is not cancelled.
- Request history uses bounded offset pages; concurrent submissions may shift
  page boundaries. Refresh to see the latest queue. Rate limits in Express are
  process-local; account cooldowns and uniqueness are database-backed.
- Identity verification is an operator responsibility. This feature does not
  implement email-address changes, automated proof of identity, or super-admin
  recovery. It does not send emails on public submission.
